01

内存地图 变量到底住在哪

C 变量不是“凭空存在”的。链接器把代码和常量放进 Flash，把全局变量、堆、栈分进 SRAM；栈和堆从 RAM 两端相向生长，中间只剩一条缝。

交互实验 示例：20 KB SRAM · STM32F1 风格地址
FLASH0x0800_0000
.text机器码
.rodata常量 / 字符串
.data 初值上电时被复制 ↓
SRAM0x2000_0000
.data已初始化全局变量
.bss未初始化 → 启动时清零 0
heap ↓
空闲 SRAM ≈ 19 KB
stack ↑
堆顶0x2000_0190
栈指针 SP0x2000_4F80
剩余空隙17.9 KB

点击「上电复位」看启动过程：.data 从 Flash 复制，.bss 清零。

代码与理解

/* 变量落在哪，由存储类别和链接脚本决定 */
int  g_init = 42;          // .data 有初值
int  g_zero;               // .bss 初值为 0
const char msg[] = "hi";  // Flash

void foo(void) {
    int local = 7;         // stack，函数返回即失效
    char *p = malloc(64); // heap，记得 free
}

为什么 .bss 不占 Flash？

未初始化的全局变量在文件里只需记一条“从哪开始、多长、全填 0”，不用真的存一堆 0。所以 .bss 只在 RAM 占空间，能省 Flash。

单片机上别随便 malloc

堆没有 MMU 保护，碎片化之后分配失败只会返回 NULL；在中断里 malloc 更危险。嵌入式更常用静态内存池或固定大小的块。

记住：Flash 放“不会变的东西”，SRAM 放“会变的东西”；栈向下长，堆向上长。

02

volatile 编译器太聪明，也是错

编译器只对“C 抽象机”负责：对普通变量，它可以把 flag 的读取提升到循环外，缓存在寄存器里。这里的“缓存”指编译器优化，不是 CPU 硬件 cache；volatile 的作用是要求编译器保留每一次访问。

动画 未运行
CPU 核心
R0—
while (flag == 0) { }
读内存
SRAM
flag0
ISR 可写
↻
循环次数 0
普通变量
等待开始…

代码与理解

uint32_t flag = 0;

void wait_ready(void) {
    while (flag == 0) {
        /* 等硬件/中断把 flag 置 1 */
    }
}

// ISR 里：flag = 1;

没有 volatile

  • 第一次读内存，之后直接用 R0
  • ISR 改了内存，CPU 看不见
  • 可能被优化成 while(1)

有 volatile

  • 编译器必须保留每次访问，不能合并或删除
  • 硬件写、ISR 写都能被看到
  • 不保证原子性，也不保证跨变量顺序

它不做什么

volatile 不是线程安全，也不是内存屏障：它不保证“先写 A 再写 B”对其他核/ISR 可见，也不让 count++ 变成原子操作。需要顺序或原子性时，用 barrier、原子指令或临界区。

三个必加 volatile 的地方

① 内存映射寄存器；② 中断与主循环共享的变量；③ 由硬件/DMA 更新的缓冲区标志。加 volatile 只解决“看得见”，共享数据的原子性和顺序仍要单独设计。

记住：volatile 要求编译器保留访问，不是硬件 cache 开关，也不是线程安全或内存屏障。

03

指针直连硬件 地址就是寄存器

在 MCU 里，外设寄存器不是特殊语法，只是“某个固定地址上的 32 位格子”。把整数强转成指针，再解引用，你就在直接改硬件。

分步执行 GPIOA_ODR · bit 5 · 示例地址
CPU
*(volatile uint32_t *)0x4001080C |= (1u << 5);
地址 0x4001_080C
0x4001 080C
总线访问
GPIOA · ODR 0x4001_080C
PA5LED
ODR = 0x0000_0000
  1. ①0x4001080C 只是一个整数。
  2. ②强转成 volatile uint32_t *：告诉编译器“这是一块 32 位、会自己变的寄存器”。
  3. ③解引用 * 得到寄存器本身；|= (1u << 5) 读出、改 bit5、写回。

执行后会看到 bit 5 被置 1，PA5 上的 LED 点亮。

代码与理解

/* 标准库通常这样封装 */
#define GPIOA_ODR  (*(volatile uint32_t *)0x4001080C)

/* 置位：读-改-写，只动 bit5 */
GPIOA_ODR |= (1u << 5);

/* 等价的“直接写”会踩坏其它位 */
// GPIOA_ODR = (1u << 5);  ✗

/* STM32 更推荐：单次写 BSRR，无读改写 */
GPIOA_BSRR = (1u << 5);          // 置位 bit5
GPIOA_BSRR = (1u << (5 + 16));   // 复位 bit5

拆开看这一行

0x4001080C → 地址；(volatile uint32_t *) → 解释方式；* → 取出那块内存；|= → 读、或、写回。

为什么必须 volatile？

这段代码里寄存器只被写一次，编译器很可能把读-改-写优化掉，或者认为“值没变”而省略。对硬件地址，每一次访问都有副作用。

记住：寄存器 = 固定地址 + 固定宽度 + volatile。RW 寄存器可用 |= / &= ~ 改位，但那是读改写；STM32 的 BSRR/BRR 是 WO，单次写即可置位/复位，不会被中断拆开。

数组与指针 地址一样，步长不一样

以 32 位指针为例：uint16_t a[5] 从 0x2000_0100 开始。点四个表达式，看指针落在哪、跨过多少字节。

uint16_t a[5];

a          // &a[0]，uint16_t *
&a         // uint16_t (*)[5]
a + 1      // 地址 + 2 字节
&a + 1     // 地址 + 10 字节

void f(uint16_t a[5]) {
    sizeof(a);  // 4，不是 10
}
a
sizeof(a) = 10 sizeof(&a) = 4 sizeof(a + 1) = 4
传参后：void f(uint16_t a[5]) { sizeof(a) /* 4 */ } 数组名作为实参退化为指针，长度信息丢失；要额外传长度。

a 和 &a 的地址相同，但类型不同：a 是首元素指针，&a 是整个数组的指针。

04

位操作 一个寄存器，三十二个开关

寄存器不是“一个数”，而是并排的 32 个开关。嵌入式 C 的一半工作，就是用位运算精确地拨动其中一个，而不碰其它 31 个。

交互实验 点击任意位格可直接拨动；按钮作用于选中的 n
GPIOA_ODR · 低 8 位 目标位 n = 3
二进制0b0000 0000
十六进制0x00
reg |= (1u << 3);

例：置位 bit3 后，ODR 变成 0x08，PA3 输出高电平。

BSRR · 单次写入完成置位 / 复位 GPIOA_BSRR · 0x4001_0810
低 16 位 · 置位写 1 → ODR 对应位变 1
高 16 位 · 复位写 1 → ODR 对应位变 0
BSRR = 0x0000_0000 ODR = 0x0000_0000

BSRR 是 WO：写 1 有效，读回无意义。单次总线写，不需要读改写。

代码与理解

/* 四个动作，背下来 */
reg |=  (1u << n);   // 置 1
reg &= ~(1u << n);   // 清 0
reg ^=  (1u << n);   // 翻转

if (reg & (1u << n)) {  // 读某一位
    /* bit n 为 1 */
}

为什么是 1u 不是 1？

1 << 31 在 32 位 int 上是有符号溢出（未定义行为）；1u << 31 才是明确的 0x80000000。

多位置位 / 位掩码

同时控制多位：reg |= (1u << 3) | (1u << 5);；清一组：reg &= ~((1u << 3) | (1u << 5));

先看访问类型，再决定写法

RW（如 ODR）：可读可写，改位可用 |= / &= ~；RO（如 IDR）：只读；WO（如 BSRR/BRR）：写入有效，读回无意义；RC_W0 等特殊类型：写 0 清零、写 1 无效果。具体以参考手册为准。

两个好用的技巧

x & (x - 1) 清掉最低位的 1；x & -x 取出最低位的 1（常用于找最高优先级中断）。

记住：对 RW 寄存器，置位用或、清位用与取反；对 WO 的 BSRR/BRR，直接单次写完成置位/复位；其它访问类型按手册处理。

05

结构体对齐 sizeof 不是成员大小相加

CPU 访问 4 字节变量时，喜欢地址是 4 的倍数。编译器于是在成员之间塞入看不见的 padding，让每个成员都“站对位置”。

交互实验 格子里标的是字节偏移 · 斜纹格是 padding
struct Sample uint8_t a; uint32_t b; uint16_t c;
sizeof12bytes
a · 1 B b · 4 B c · 2 B padding

默认布局：a 后面补 3 B，c 后面补 2 B，总共 12 B。

代码与理解

struct Sample {
    uint8_t  a;  // offset 0
    uint32_t b;  // 需要 4 对齐 → offset 4
    uint16_t c;  // offset 8
};                // sizeof = 12（尾部补齐到 4）

_Static_assert(sizeof(struct Sample) == 12,
               "layout changed");

三条对齐规则

① 每个成员的偏移必须是它自身对齐数的倍数；② 结构体总大小补齐到最大成员对齐数的倍数；③ 数组元素之间也要满足这个大小，否则第二个元素就错位了。

packed 不是免费的

打包后成员可能落在非对齐地址。编译器知道成员被 packed 时，可以生成逐字节访问；把非对齐地址当作普通整型指针访问，则可能变慢或触发异常，取决于内核、指令与设置。协议解析优先显式拼字节，DMA/寄存器布局以手册为准。

记住：想省空间，先按成员大小从大到小排；想跨平台传数据，再考虑 packed + 显式序列化。

06

大小端 0x12345678 长什么样

多字节数据在内存里总得有个先后。Cortex-M 默认小端：低地址放低位字节；网络协议和不少传感器用大端。搞反了，读出来就是 0x78563412。

交互实验 切换存储顺序，或交换数值的字节
uint32_t x = 0x12345678
0x2000_0000+1+2+3
uint8_t *p = (uint8_t *)&x;
p[0] = 0x78 （最低有效字节）

小端：低地址存低位字节，所以 p[0] 读到 0x78。

首字节 0x7F → 0x80：拼接时先转 uint32_t
int32_t v = buf[0] << 24; 0x7F000000 最高位为 0，暂时没溢出
uint32_t v = (uint32_t)buf[0] << 24; 0x7F000000 先转无符号，结果明确

0x7F 只是侥幸；把首字节调到 0x80，看有符号左移会怎样。

代码与理解

/* 判断本机字节序（面试常考） */
uint16_t v = 0x0102;
uint8_t *p = (uint8_t *)&v;

if (p[0] == 0x02) {
    /* 小端：低地址是低位 */
} else {
    /* 大端 */
}

什么时候会踩坑

串口/网络收到的多字节帧、SPI 传感器寄存器、Flash 里的文件头、以及用 memcpy 直接把字节数组当结构体用。

可移植的写法：先转 uint32_t 再移位

别用指针强转直接解析协议。逐字节拼时写成 val = ((uint32_t)buf[0] << 24) | ...；若直接写 buf[0] << 24，在 32 位 int 上首字节 ≥ 0x80 可能触发有符号左移溢出（UB）。

两个问题要分开

“内存里的字节顺序”和“拼出来的数值”是两件事：小端机器上直接 memcpy 到 uint32_t 会按本机顺序解释；协议里则要按协议规定的字节序逐字节拼。按协议顺序拼接后，已经得到正确数值，不要再重复交换字节。htonl/ntohl 用于主机序与网络序转换，__REV 则直接反转四个字节。

记住：“字节序”只影响内存里的排列，不影响变量的数值；用 uint8_t* 才能看见它。

07

中断与共享数据 count++ 不是一步

一条 C 语句，编译后可能是三条指令：读、加、写。中断只要插在读和写之间，两次自增就会合并成一次——这就是“丢失更新”。

单步动画 主循环与 ISR 都在操作同一个 count
r0—
count5
主循环 ISR
? 按「单步」或「播放」走完整个交错过程，看看 count 最后是多少。

代码与理解

volatile uint32_t count = 5;

void TIM_IRQHandler(void) {
    count++;              // 也可能丢更新
}

int main(void) {
    while (1) {
        uint32_t primask = __get_PRIMASK();
        __disable_irq();
        count++;          // 读—改—写全在临界区
        __set_PRIMASK(primask); // 恢复原状态
    }
}

volatile 救不了原子性

volatile 只保证每次访问内存，不保证“读-改-写”不被打断。对齐的 32 位 SRAM 变量在本例 Cortex-M 上单次读写通常是原子的，但 ++ 不是。

临界区要覆盖整个 RMW

关中断必须发生在第一次读之前，恢复要放在写回之后。退出时恢复保存的 PRIMASK，不要无条件 __enable_irq()：如果调用前本来就关着中断，恢复后仍应关着。

三种解法

① 保存 PRIMASK → 关中断 → 读改写 → 恢复；② 让 ISR 只置标志，主循环处理；③ 用原子指令（如 LDREX/STREX）或无锁环形缓冲。

记住：临界区要包住整个“读-改-写”，退出时恢复原来的中断屏蔽状态；ISR 越短越好。

08

const 与指针 到底锁住了谁

看 const 在 * 的哪一边：在左边，锁“指向的数据”；在右边，锁“指针自己”。两边都有，就都别动。

点击试试 试着修改被锁住的部分，看编译器是否放行
const char *p锁数据
p0x1000
→
'H''i'

指针可以改指向；*p = 'x' 不行。

char * const p锁指针
p0x2000
→
'H''i'

数据可以改；p = q 不行。

const char * const p全锁
p0x3000
→
'H''i'

只读视图：既不能改指向，也不能改内容。

代码与理解

/* 读法：const 在 * 左边 → 数据只读 */
const char *p;        // *p 只读，p 可变

/* const 在 * 右边 → 指针只读 */
char * const p;        // p 只读，*p 可变

/* 两边都有 → 都只读 */
const char * const p;

一个顺口溜

“const 默认修饰它左边的东西；左边什么都没有（位于最左），才修饰右边。”

所以 const char *p 锁的是 char（数据）；char * const p 左边是 *，锁的是指针本身。

函数参数里的 const

void uart_send(const uint8_t *buf, size_t len) 表示函数不会改你的缓冲区，是接口契约，也让调用方能传 const 数据。

记住：先找 *，再看 const 在哪边；它保护的是“通过这个指针不能做什么”。

09

整数陷阱 for (uint8_t i = 0; i < 256; i++)

比 int 窄的类型在表达式里会先“提升”成 int；无符号数减法会回绕；有符号左移溢出是未定义行为。三件事叠在一起，就是嵌入式最常见的死循环。

动画 uint8_t 的取值只有 0–255
uint8_t i 0
0 … 255
循环次数0
条件 i < 256永远成立
点「运行」看 i 走到 255 之后发生了什么。
uint8_t a = 200, b = 100; a + b = ?整型提升

表达式里 a、b 先提升为 int，所以 a + b 是 300，比较/打印都正常。

但赋值回 8 位：uint8_t c = a + b; 只保留低 8 位，c = 44（300 − 256）。

if (-1 < 0u) ...隐式转换

比较时 -1 被转换成 unsigned int，变成 4294967295，所以条件是 false。

编译器通常会警告 comparison of integer expressions of different signedness，别忽略它。

1 << 31未定义行为

1 是有符号 int，左移 31 位把 1 移进符号位，在 C 标准里是未定义行为，不同优化等级结果可能不同。

写 1u << 31，得到明确的 0x80000000。

uint8_t x = 0; x--;无符号回绕

无符号运算按模 2⁸ 回绕，结果是 255，不是 −1。用 int8_t 才是 −1。

倒计时循环别写 for (uint8_t i = n; i >= 0; i--)，条件永远成立。

代码与理解

/* 死循环：i 永远 < 256 */
for (uint8_t i = 0; i < 256; i++) { }

/* 正确：用更宽的类型，或改条件 */
for (uint16_t i = 0; i < 256; i++) { }

/* 有符号溢出：也是 UB */
int32_t big = INT32_MAX;
big++;   // 未定义，不是“变成最小值”

为什么 i < 256 永远成立？

uint8_t 在比较前被提升为 int，所以是 0..255 < 256，恒真；而 i++ 又在 8 位里回绕到 0。

打开警告

-Wall -Wextra -Wconversion -Wsign-compare。很多“玄学 bug”在编译器的警告里已经写着了。

记住：窄类型会提升成 int；无符号会回绕；有符号溢出是 UB。循环变量优先用 int/size_t。

启动流程与栈 上电后并不是直接进 main

复位后，CPU 先从向量表取初始栈指针，再跳到 Reset_Handler；启动代码把 .data 搬进 RAM、把 .bss 清零，才调用 main。栈向下生长，局部数组太大就会撞车。

启动代码跑完，C 语言才有“已初始化的全局变量”和“全 0 的 .bss”可用。

代码与理解

/* 启动文件（简化）*/
extern uint32_t _sdata, _edata, _sidata;
extern uint32_t _sbss, _ebss;

void Reset_Handler(void) {
    SystemInit();
    /* .data: Flash → SRAM */
    memcpy(&_sdata, &_sidata, ...);
    /* .bss: 全部写 0 */
    memset(&_sbss, 0, ...);
    main();
    while (1) { }
}

栈溢出不一定立即报错

RTOS 里任务通常有自己的栈；裸机常用 MSP，也可以配置线程模式使用 PSP。大局部数组、深递归、sprintf 都会吃栈。溢出后改坏的是相邻内存，症状可能完全无关。

怎么防

① 大缓冲区放 static 或全局；② 用 sizeof 检查拷贝长度；③ 栈尾放“魔数”定期检查；④ 启用 MPU 或 RTOS 的栈水位检测。

记住：启动代码建立 C 运行环境；栈向下长，函数返回后局部变量立刻失效。

#define 它只是文本替换，不是函数

预处理器在你的代码进入编译器之前，按 token 做“查找—替换”。它不懂类型、不建作用域、也不会替你加括号。所有宏的坑，几乎都来自这一句话。

多条语句的宏：为什么要 do { } while (0) 
/* 展开后的代码 */
if (ok)
    printf("[%s] ", TAG);
printf("%s\n", "hi");
else
    puts("no");

宏体里的两条语句只有第一条被 if 管住，else 悬空 → 语法错误。

代码与理解

/* 错：参数和整体都没有括号 */
#define SQ(x)  x * x

SQ(a + 1)      // → a + 1 * a + 1
SQ(2 + 3)      // → 2 + 3 * 2 + 3

/* 对：参数、整体都加括号 */
#define SQ(x)  ((x) * (x))

/* 括号救不了副作用：n++ 展开两次，修改未排序 → UB */
SQ(n++);       // → ((n++) * (n++))

/* 多条语句：do-while 包成一条 */
#define LOG(msg) do { \
    printf("[%s] ", TAG); \
    printf("%s\n", msg); \
} while (0)

预处理器只做三件事

展开头文件、替换宏、处理条件编译。它不解析类型、不认识作用域，也不做参数检查。

三条铁律

① 参数出现的地方都加括号；② 整个宏体再加一层括号；③ 参数只求值一次，别把 i++ 传进去。

能不用宏，就别用宏

常量优先 enum / const，短函数优先 static inline。宏只留给需要 token 操作的场合：寄存器、日志、X-Macro。

记住：写宏体时要假设参数是任意一段 token；括号能修优先级，修不了重复求值。

预处理器的武器库 条件编译、#、## 与 X-Macro

#define 不只是常量。它能在编译前删代码、拼标识符、生成整张表；用好了是零开销抽象，用过头就是没人能调试的“宏魔法”。

三个实验 改开关 / 点展开，观察预处理器的输出
① 条件编译：把代码从编译单元里“剪”掉 
#define DEBUG 0

void report(int x) {
#if DEBUG
    printf("x = %d\n", x);
#else
    (void)0;
#endif
}
预处理之后 → 交给编译器
void report(int x) {
    /* printf 被预处理器删除 */
    (void)0;
}

DEBUG=0：#if 块整段消失，编译器根本看不到 printf。

② # 字符串化 / ## 拼接：操作 token 本身
GPIOA --#--> "GPIOA"
# 把紧随的参数原样变成字符串字面量。

字符串化常用于把枚举名、寄存器名打印出来。

③ X-Macro：一张表，生成三份代码
一张引脚表
#define PIN_TABLE(X) \
  X(LED,  A, 5) \
  X(BTN,  C, 13) \
  X(UART, A, 9)

#define AS_ENUM(name, port, pin)  PIN_##name,
#define AS_NAME(name, port, pin)  #name,
#define AS_INIT(name, port, pin)  { GPIO##port, pin },

PIN_TABLE(AS_ENUM)   // 生成 enum

展开结果 · enum

    PIN_LED,
    PIN_BTN,
    PIN_UART,
    PIN_COUNT
};

改一处表，三处同步；引脚增删不再漏改。

代码与理解

/* 头文件保护 */
#ifndef CONFIG_H
#define CONFIG_H
/* ... */
#endif

/* 条件编译 */
#if defined(BOARD_A) && DEBUG
/* 只有 BOARD_A + DEBUG 才编译 */
#endif

/* 字符串化 / 拼接 */
#define STR(x)        #x
#define XSTR(x)       STR(x)
#define CONCAT(a, b)  a##b

/* 可变参数日志 */
#define LOG(fmt, ...) \
    printf("[%s:%d] " fmt "\n", \
           __FILE__, __LINE__, ##__VA_ARGS__)

为什么需要两级字符串化？

# 会阻止参数展开：STR(__LINE__) 得到的是 "__LINE__"；加一层 XSTR 才会先展开成行号。

__FILE__"main.c"
__LINE__42
__DATE__Nov 4 2026
__TIME__13:30:00
__STDC_VERSION__201710L
__func__不是宏

四个容易翻车的地方

① 头文件保护只防重复包含，不防重复定义；② #if 里未定义的标识符按 0 处理，建议开 -Wundef；③ 可变参数为空时，##__VA_ARGS__ 是 GNU 扩展，C23 用 __VA_OPT__；④ 宏名全大写，别和变量重名。

宏 vs 其它零开销抽象

常量优先 enum / const，短函数优先 static inline，需要“生成代码”时才用宏。宏没有类型检查，调试器也看不到展开前的名字。

记住：宏是编译前的代码生成器；能力越大，越要限制在头文件和命名约定里。

带走这张图 嵌入式 C 生存清单

不需要背十页笔记。把下面几行贴在显示器边上，能躲掉大多数“玄学 bug”。

访问硬件 *(volatile uint32_t *)0x4001080C

固定地址 + 宽度 + volatile，每一次访问都有副作用。

四个位操作 reg |= 1u << n; reg &= ~(1u << n); reg ^= 1u << n; if (reg & (1u << n))

置位、清位、翻转、判断；只动目标位。

共享变量 static volatile uint32_t tick;

ISR 与主循环共享要 volatile；读-改-写还要临界区。

临界区 uint32_t pm = __get_PRIMASK(); __disable_irq(); count++; __set_PRIMASK(pm);

覆盖整个读-改-写；退出时恢复原来的 PRIMASK，不要无条件开中断。

布局检查 _Static_assert(sizeof(S) == 12, "");

结构体一旦跨模块/跨版本使用，用静态断言锁住布局。

协议解析 v = ((uint32_t)b[0] << 24) | (b[1] << 16) | …

先转成无符号再移位，避免 0x80 左移触发 UB；别把字节数组直接强转成结构体。

循环变量 for (int i = 0; i < 256; i++)

别用 uint8_t 数 0..255，它会在 255 之后回绕。

延时 for (volatile int i = 0; i < N; i++);

空循环会被优化掉；精确延时用定时器，别靠数指令。

宏的三条铁律 #define SQ(x) ((x)*(x)) do { ... } while (0)

参数与整体都加括号；多语句用 do-while；参数别带副作用。

再拆三个常见误解

“volatile = 线程安全”不。它只要求编译器保留访问，不提供原子性和顺序保证。
“sizeof(struct) = 各成员之和”不。有 padding 和尾部补齐，顺序也会影响大小。
“局部变量会自动清零”不。具有静态存储期且未显式初始化的对象会被零初始化；未初始化的自动变量值不确定，不能当作随机数读取。
